# 「产品克制」Skill 设计文档

日期:2026-05-29

## 一句话定位

一个**默认怀疑**的独立评审 skill:用户主动描述一个产品/功能/创业想法,skill 用成熟的产品、用户、商业、市场框架过一遍,输出"可行性评价 + 简要概述 + 详细说明"三部分。目标不是帮用户把想法做出来,而是帮用户判断**值不值得做**,以及如果做,最先该用最小成本验证什么——让用户在 AI 让一切都"能快速落地"的时代保持理性和克制。

## 背景与动机

AI 工具能力增强后,大量产品可以被快速落地,但其中大部分是不成熟的想法。盲目落地带来 token 消耗、成本增加,却没有真正价值。需要一个"冷静的产品顾问",在动手前先泼一盆理性的冷水。

## 关键设计决策(已与用户对齐)

| 维度 | 决策 |
|---|---|
| 形态与触发 | **独立评审 skill**——用户主动调用并描述想法;评审前先走一轮「提问闸门」(逼问式,最多 6 问,选择题),再按一次性评审输出 |
| 默认立场 | **默认怀疑,举证责任在用户**——只有扎实证据才能把判断往好调 |
| 评审范围 | **通用产品想法**(AI 产品是其中一类,非唯一) |
| 结论形式 | **多维度评分卡**(红/黄/绿 + 一句话理由)|

## 核心原则(skill 的"性格")

1. **举证责任在用户**:每个维度默认从"红灯"起步,只有用户描述里有扎实证据才往绿调。说不清 = 风险,不是中性。
2. **缺失即风险,先逼问再判更红**:评审前先走「提问闸门」就六维关键空白当面发问;能答变评分证据,当面问到仍答不上则该维判更红。非交互环境无法发问时回退一次性评审、说不清的维度直接判红。举证责任始终在用户。
3. **拒绝套话否定**:每个红灯必须给**具体到这个想法**的理由。禁止"护城河不够""需求不真"这类放之四海皆准的空批评——否则 skill 等于没用。
4. **冷静,不留情,但对事不对人**:不嘲讽、不制造焦虑,也不和稀泥。
5. **给放行路径,但门槛高**:结论可以是"可以试",需附"最该先验证的一件事";结论是"别做",也要给"什么条件下才值得重启"。

## 评审框架(弹药库)

### 用户思维 —— 真需求还是一厢情愿?
- **The Mom Test**:警惕恭维、假设性空话、愿望清单三类垃圾信号;问过去行为而非假设。判据:用户没在花时间/花钱解决,就不是真问题。
- **维生素 vs 止痛药**:没有会痛(止痛药,销售周期短、用户追着要、收益可量化)还是有了更好(维生素,慢热、定性、可有可无)。
- **Paul Graham 拷问**:现在谁迫切想要,迫切到愿意用烂烂的 v1?

### 产品思维 —— 能不能成立?
- **Marty Cagan 四大风险**:价值风险、易用性风险、可行性风险、商业可行性风险。
- **Premortem(事前验尸)**:假设产品已经失败,倒推它怎么死的。

### 商业思维 —— 生意成立吗?
- **单位经济**:每笔交易赚不赚钱?成本(含 token/算力)扛得住吗?(参考:纯 wrapper 毛利约 40%,远低于健康 SaaS 的 70–80%)
- **护城河 / 防御性**:别人明天能照抄吗?大厂下个版本会不会顺手干掉?

### 市场思维 —— 池子够大、时机对吗?
- **TAM / SAM / SOM**:总盘子、可触达、能拿下。
- **Why now**:为什么偏偏现在能成?之前为什么没成?

### AI 产品专项(识别到是 AI 产品时自动追加)
- 薄壳 wrapper 的高流失(常在前 90 天流失大部分用户)。
- 基座模型升级抹平价值;真护城河在垂直工作流整合、行业 know-how、系统级数据连接、按结果付费。

## 评分卡维度(6 项,各给 红/黄/绿 + 一句话具体理由)

| 维度 | 来自 | 一句话拷问 |
|---|---|---|
| 真需求度 | Mom Test / 止痛药 vs 维生素 | 用户现在为这问题花钱花时间了吗?没有会痛还是有了更好? |
| 价值与差异 | Cagan 价值风险 / 护城河 | 凭什么是你?别人明天能照抄?大厂顺手干掉? |
| 可行性 | Cagan 可行性风险 | 用现有的人/时间/技术真做得出来吗? |
| 商业账 | 单位经济 | 每笔交易赚钱吗?成本(含 token)扛得住吗? |
| 市场与时机 | TAM/SAM/SOM / Why now | 池子够大吗?为什么偏偏是现在能成? |
| 克制度 | 机会成本 | 真有人要,还是"因为能做所以做"?不做会怎样? |

## 输出结构(三部分)

1. **可行性评价(评分卡)**:6 维度红黄绿 + 总体倾向(别做 / 再想想 / 可以试)。
2. **简要概述(3-5 句)**:一眼看完——总体判断 + 最致命的 1-2 点。
3. **详细说明**:
   - 逐维度展开理由(每条具体到这个想法);
   - **Premortem**:假设它已经失败,倒推它怎么死的;
   - **「如果你一定要做,先花最小成本验证的那一件事」**。

## HTML 报告设计

HTML 报告是三部分评审的可转发版本,不是第二套判断。它的首屏要像一页决策备忘录:读者不需要通读全文,也能立刻看到总体倾向、下一步动作、证据充分度、最大缺口和六维风险分布。下面再给评分卡、简要概述、详细说明、Premortem、最小验证动作和重启/放行条件。

报告生成前先形成一份内部数据快照:总体倾向、六维灯色、灯色计数、首屏一句话、下一步动作、证据充分度、已确认事实、关键假设、最大缺口、逐维理由、Premortem、最小验证动作、重启/放行条件。HTML 各区块都从这份快照取数,避免首屏、评分卡和详细说明出现不一致。

正文阅读密度采用「推荐留白」方案:章节之间、评分卡行、简要概述、逐维说明和三个强调块都要比首版更松,让读者在红/黄/绿判断之间有停顿;但不走宽松杂志版,避免报告变成长卷、削弱决策备忘录的效率。

证据充分度按用户提供的信息来判:只有一句想法或提问闸门答不上来 = 低;有明确用户、场景和部分验证但缺少付费或行为证据 = 中;有真实行为、付费或可核实数字 = 高。雷达只表达红/黄/绿风险分布,不当作精确量化评分。

## 交付物

一个标准 Claude Code skill:`SKILL.md` + 评审框架与示例。后续用 `skill-creator` 落地。安装位置默认 `~/.claude/skills/`(全局可用,不绑定本仓库)。

## 非目标(YAGNI)

- 不做前置拦截或全程陪伴形态(本期只做独立评审)。
- 不做多轮反复追问;但评审前有一轮「提问闸门」(最多 6 问,选择题)——这是**逼问式举证**而非温柔澄清:能答变证据,答不上判更红,非交互则回退一次性评审。
- 不做 Web 自动市场调研(基于用户提供的信息 + 内置框架判断)。
- HTML 报告不额外发明新结论;它只把正文评审重排成更适合阅读、转发和打印的形态。
