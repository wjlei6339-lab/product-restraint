# 评审前「提问闸门」Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 在 `product-restraint` skill 的评审流程前插入一个最多 6 问的「提问闸门」(前 3 收集需求、后 3 灵魂拷问,均走 `AskUserQuestion` 选择题),把「缺失即风险」升级为「先逼问·答不上更红」,并同步三处文档不变量。

**Architecture:** 纯 prose 改动。交付物是 skill 正文,不是可编译代码。每个任务 = 对某文件做一处精确文本替换(给出逐字的"原文→改后"),改完读回确认,最后跑 `./test.sh` 验证非交互回退路径不破坏老行为。无自动断言,验证靠读回 + 人工对照五条不变量。

**Tech Stack:** Markdown prose;`AskUserQuestion` 工具;`./test.sh`(`claude -p` 批处理 eval,非交互)。

**关键约束(改完不能破坏的五条不变量):**
1. 默认怀疑,举证责任在用户 —— 保留
2. 缺失即风险 —— **本次唯一被改写**:升级为"先逼问,答不上更红"
3. 拒绝套话否定 —— 保留并强化(红灯理由要引用用户的具体选择)
4. 三部分输出模板,顺序固定 —— 保留(闸门在三部分之前,不动三部分本身)
5. 给放行路径但门槛高 —— 保留

> 所有"原文"均取自当前 `SKILL.md` / `CLAUDE.md` / `docs/design.md`。若文件已被改动导致原文匹配失败,先 Read 对应文件、按语义定位后再改,不要盲目替换。

- **非交互回退**:如果当前环境无法发问(`AskUserQuestion` 不可用,例如 `claude -p` 批处理、或没有可应答的真人),**跳过整个闸门**,直接进第 1 步,按一次性评审走,说不清的维度按"缺失即风险"判红。
- **逼问不是澄清**:每个问题的选项都要能区分"有证据"和"脑补/没做"。用户选了暴露空白的选项、或用 Other 写含糊话,对应维度**直接判更红**,并在详细说明里点明"当面问到都答不上,比没问更说明问题"。

**第一批 · 收集并确认需求**(对应 真需求度 / 价值与差异 / 商业账):

- **付费 / 使用意愿**:用户愿意为它付费或高频使用吗?——选项区分「已经有人为类似东西付过钱」「应该会愿意吧」「免费才会用」。

**第二批 · 灵魂拷问**(故意扎心,逼用户对号入座,对应 克制度 / 真需求度):

- **需求从哪来**:这个想法的真实来源是?——选项区分「见过 ≥5 个真实用户主动抱怨这个问题」「主要是我自己想要(n=1)」「因为 AI 让它能做了,所以想做」。
